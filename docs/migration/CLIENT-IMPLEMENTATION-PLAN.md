## 目标与非目标

以自有品牌分发现有客户端，使普通用户沿用原交互登录、获取与原方案相同的站点数据，并通过站点使用原有 agent 能力。服务端继续 New API rc.37 小改和内嵌网页；两个仓库以版本化 API 契约分别维护。

不做管理员端、扩展聊天云同步、重写 GPUI/agent 引擎、整体替换 New API、拆网页、强制完整 staging 或擅自上线。详见[用户确认决策](DEPLOYMENT-DECISIONS.md)。

## 已发现的发布阻断（静态证据，非联调验收）

[兼容性审计](CLIENT-COMPATIBILITY-AUDIT.md)第 7–9 节已确认，未经适配的 rc.37 不能直接满足原客户端合同：

- 客户端原登录桥 `/auth/paseo`、桌面 code/verifier exchange 和 JSON refresh token，与 rc.37 的登录接口、refresh cookie 及绝对到期时间不同；桥服务是否已存在尚未确认。
- 原 `/api/v1` 的响应 envelope、账户/分组 DTO 与 rc.37 `/api` 不同，路径重写不能替代协议/语义转换。
- 原客户端需要可用 gateway key；rc.37 token 列表使用掩码 key，创建响应不直接返回原 ApiKey，须核验创建后定位、明文取 key、分页和分组映射。
- 原方案包含订阅窗口、目录价格、用量、推荐、公告及独立支付中心合同。部分等价数据来源尚未证明；不以空数组/零值伪造“同步成功”，也不未经确认默默删减原范围。
- rc.37 已有 `/v1/responses`，不要误报为缺失；各 CLI/provider 的最终 URL、key 与流式行为仍需隔离联调。

因此最小方案不是只改品牌和域名，而是“品牌/安装发行配置 + 必要协议适配”。M-002 将已发现差异补成完整契约与逐文件写集，M-003 再实现；适配位于 client 边界、现有桥或 server 小模块，由矩阵决定，不默认新增第三项目或替换认证。以上均未证明生产已部署或 runtime 已通过。

## 实施原则

1. 保留原认证交互和数据范围，按真实请求/DTO证明后端缺口。URL或Nginx路径改写不能转换Token语义或补响应字段。
2. 可直连不包装；缺口评估薄兼容模块，位置由接口矩阵决定。没有依据不引入第三仓库/大型认证服务。
3. “沿用方案”不免除凭据与权限验证。认证实现遵循服务端AGENTS安全要求；账户令牌与模型key分开，不在日志/UI/fixtures暴露。
4. 不自动上传原本本地保存的聊天、工作区内容。mock用于离线测试，不证明生产已支持。
5. 新逻辑尽量独立模块、最小hook；网络/持久化IO不进入render/测量热路径，保留键盘和系统减少动态效果行为。
6. `client.tsyqapi.top` 是拟定客户端入口，不未经核验同时当作relay/安装包/更新入口；域名隔离不等于数据库或负载隔离。
